TECHNICAL DOCUMENTATION

How Edge Tutor works under the hood.

Edge Tutor is an offline AI tutoring workload designed to explore hardware/software co-design on resource-constrained edge systems. This documentation describes the technical architecture, evaluation flow, optimization process, and experimental methodology behind the project.

Architecture boundary

The native tutor executes the selected Qwen model. The gem5 path executes a focused attention proxy. These are related evaluation paths, but the proxy is not a complete execution of Qwen2.5 inference.

02 · CHIA

CHIA Loop

The current implementation organizes candidate execution through validation, mapping, software and hardware evaluation, verification, and structured result recording. Candidate search may be deterministic or optionally assisted by Gemini, while deterministic validation remains authoritative.

01
Candidate configuration

A proposed software/hardware configuration enters the experiment pipeline.

02
Schema and semantic validation

Configuration structure, supported values, cross-knob constraints, and runtime preconditions are checked.

03
Runtime mapping

Candidate settings are mapped to the native Qwen/llama.cpp and gem5 execution interfaces.

04
Native tutor evaluation

The selected Qwen2.5 Q5_K_M workload is evaluated through the CPU inference path.

05
gem5 proxy evaluation

The attention proxy runs under the corresponding hardware configuration.

06
Verification and metrics

Completion, numerical checks, hardware metrics, application metrics, and correctness evidence are validated.

07
Structured record

The candidate, requested and executed settings, metrics, versions, hashes, and provenance are persisted.

08
Next candidate

Search controls determine whether another candidate should be evaluated.

Gemini's role

Gemini is integrated as an optional candidate proposer. Its output is treated as untrusted structured data and passes the same deterministic schema, design-space, semantic, duplicate, and execution checks as deterministic candidates.

Production state

The deterministic full-loop implementation is substantially implemented. Final integrated Qwen + gem5 server acceptance remains an active validation gate.

Important quantization distinction

Q5_K_M is the quantization of the actual tutor model. Q4 in the gem5 path refers to the proxy's quantized KV-cache representation. These are separate design choices and should not be interpreted as the tutor model being Q4.

Quality vs. systems cost

The Q5_K_M baseline was selected after controlled comparison with smaller quantized alternatives. The selection emphasized factual answer quality together with artifact size, runtime behavior, and CPU resource pressure.

04 · SIMULATION

gem5 Proxy

Full Qwen inference is not currently simulated directly in gem5. Instead, the project uses an attention-focused architectural proxy to study hardware behavior under controlled configurations.

Why use a proxy?

Simulating complete modern LLM inference at detailed architectural level can be expensive. A focused attention proxy allows the project to explore cache, execution, and memory behavior while keeping experiments computationally manageable.

Real model vs. proxy

The verified Qwen model has 14 query heads, 2 KV heads, head dimension 64, and 24 layers. The current proxy uses 4 query heads, 2 KV heads, head dimension 32, and 1 layer. The proxy therefore represents a focused architectural workload, not an exact reproduction of the full Qwen model.

Proxy validity

Proxy fidelity and calibration remain active validation areas. Proxy measurements should not be interpreted as measurements of complete Qwen inference unless the relationship has been explicitly validated.

Quality metric

The current deterministic evaluation uses required-concept coverage as an initial reproducible quality signal. It is not a human judgment and does not establish educational effectiveness. Larger held-out evaluation and human review remain future validation work.

07 · OPTIMIZATION

Optimization Strategy

The project treats hardware/software configuration as a multi-objective search problem. The active implementation places deterministic validation and execution policy around the search, while Gemini can optionally propose candidate changes.

P

Pareto analysis

Candidate configurations can be compared across multiple objectives rather than reducing every experiment to one independent metric.

C

Constraints

Invalid or infeasible configurations are rejected before expensive evaluation.

↔

Candidate search

Deterministic candidates are supported by default. Gemini may optionally propose candidates inside the reviewed search space.

Search authority

Gemini does not decide whether an invalid candidate executes. Candidate iteration limits, duplicate handling, repeated-failure stopping, numerical checks, and policy validation remain deterministic program logic.

Objective policy

The exact weighting and normalization of objectives should be reported from the active optimization policy. Where a final policy value is not fixed, it should remain marked TBD / Under validation.

08 · METHODOLOGY

Experiment Methodology

Experiments are structured so that differences between candidates can be attributed to the variables being studied while preserving the provenance required to reproduce the result.

Controlled variables

Model identity, Q5_K_M quantization, runtime configuration, fixed hardware parameters, proxy shape, seeds, and other controlled settings are recorded with candidate results.

Candidate variables

The active software search includes temperature and maximum output tokens. The hardware search includes CPU model, frequency, issue width, L1D and L2 parameters.

Repeated measurements

Native benchmark and proxy experiments use explicit repetition settings where defined by the experiment contract.

Proxy calibration

Native context sweeps, gem5 proxy sweeps, sensitivity cases, normalized trends, and correlation analysis are used to study whether the proxy captures useful architectural behavior.

Calibration protocol

The current calibration sweep covers context lengths 128, 256, 512, 1024, and 2048 tokens. Calibration retains finite raw numerical errors even when reviewed tolerance is exceeded so that the complete sweep can be analyzed.

Q5 model selection evidence

In the controlled 20-question comparison, Qwen2.5-0.5B Q5_K_M achieved a 90.0% manual factual score and was selected as the initial software baseline.

Proxy execution evidence

The current Q4 attention proxy has completed verified gem5 execution under the defined two-core baseline configuration.

Calibration evidence

The proxy-fidelity protocol includes native and gem5 context sweeps, hardware sensitivity cases, normalized trends, and correlation analysis.

Integrated campaign

The final Qwen/llama.cpp + gem5 combined acceptance run has not yet been completed. It remains an active validation gate.

Current calibration observation

The first 128-token server simulation produced finite numerical errors but exceeded the reviewed Q4 tolerance: maximum absolute error 0.010727912 and MSE 0.000012264. The production loop remains fail-closed when tolerance is exceeded; calibration records the violation and continues the sweep for analysis.

What is intentionally not shown

No broader optimization ranking, Pareto winner, or final Qwen-plus-hardware performance conclusion is presented until the integrated campaign and validation evidence are complete.

11 · VALIDITY

Validity & Limitations

Explicitly documenting the boundaries of the current methodology is essential for interpreting the results correctly.

Proxy scope

The current gem5 workload is an attention-focused proxy and should not be presented as a complete simulation of Qwen inference.

Unmodeled components

FFN/MLP computation, tokenization, sampling, and complete llama.cpp runtime behavior are outside the current proxy scope.

Calibration status

Proxy calibration is still being evaluated. The first 128-token case exceeded the reviewed numerical tolerance, so the proxy relationship remains under validation.

Different timing meanings

Native application latency, simulated time, and simulator host runtime are distinct measurements and must not be compared as though they represent the same quantity.

Model vs. proxy quantization

Q5_K_M is the selected real-model quantization. Q4 is used in the proxy's KV-cache representation. These are separate representations.

Evaluation quality

Required-concept coverage provides a deterministic initial quality signal. It is not a substitute for larger held-out evaluation or human assessment.

Interpretation rule

Proxy results describe the architectural behavior represented by the proxy. They should not automatically be interpreted as end-to-end tutor performance.
