An AI tutor that works without internet.

Why offline

Four good reasons

Sending every question to a server works fine — until the connection drops, the bill arrives, or a student would rather nobody saw what they got wrong.

📴

Works offline

On a bus, in a village with no signal, during a power cut — the tutor still answers.

🔒

Stays private

Questions and mistakes never leave the desk. Nothing is uploaded anywhere.

💸

Costs little

No fee per question and no servers to keep running for every classroom.

🔌

Fits small hardware

Designed for the modest, affordable chips schools can actually buy in bulk.

Here's the catch: you can't have everything at once.
The problem

Three things pulling against each other

Make the tutor faster and it needs more memory. Save memory and it slows down. Fix both with a better chip and the price goes up. Push any one lever and the other two react.

So we design the program and the chip together — not one after the other.
Our approach

Two sides, designed as one

Normally someone writes the software, then someone else picks the hardware and hopes for the best. We change both at the same time and see which combinations actually work well together.

Simulating a whole AI model chip-by-chip would take forever. So we test the part that matters most.
The shortcut

Test the busiest part, not the whole thing

Inside every AI model there's a step called attention — where the model decides which earlier words matter for the next one. It's the step that eats most of the time and most of the memory. If we get attention right, we've got the hard part right.

These are the dials. We turn them in every sensible combination.
What we tune

The dials we turn

Five on the software side, five on the hardware side. Each one shifts the balance between speed, memory and price.

💻 The program
Memory format
How tightly we compress what the model remembers.
Conversation length
How much of the chat the tutor keeps in mind.
Number of “readers”
How many things the model looks at in parallel.
Detail per reader
How much detail each of those looks holds.
Parallel workers
How much of the work is split up and done at once.
🔧 The chip
Number of cores
How many jobs the processor can handle at once.
Clock speed
How quickly it works through each step.
Fast memory size
The small scratchpad right next to the processor.
Scratchpad layout
How that scratchpad is organised internally.
Main memory
The bigger, slower storage it falls back on.
For every setting we turn, we write down three kinds of result.
What we measure

Three scorecards

⚡

Speed

Cycles — total work done
Instructions — steps taken
Efficiency — work per step
Time — how long it would really take
🗄️

Memory behaviour

Near misses — times the scratchpad was empty
Far misses — times it had to reach further out
Fewer misses means a faster, cooler chip.
✅

Correctness

Checksum — the answer is verified
Pass / fail — a fast run that gets it wrong doesn't count
Every single experiment goes around this loop.
How we test

One trip around the loop

Pick a setting. Check it makes sense. Run it on both sides. Collect the numbers. Compare it against everything tried before — then pick the next setting.
