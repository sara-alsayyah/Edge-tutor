Hi! I'm Maya. Let me walk you through Edge Tutor — no technical background needed.

An AI tutor that works without internet.

A student asks a question. A small AI model answers — running entirely on a cheap little computer sitting right there on the desk. No Wi‑Fi. No cloud. No monthly bill.

Why offline

Four good reasons

Sending every question to a server works fine — until the connection drops, the bill arrives, or a student would rather nobody saw what they got wrong.

Works offline

On a bus, in a village with no signal, during a power cut — the tutor still answers.

Stays private

Questions and mistakes never leave the desk. Nothing is uploaded anywhere.

Costs little

No fee per question and no servers to keep running for every classroom.

Fits small hardware

Designed for the modest, affordable chips schools can actually buy in bulk.

The problem

Three things pulling against each other

Make the tutor faster and it needs more memory. Save memory and it slows down. Fix both with a better chip and the price goes up. Push any one lever and the other two react.

Here's the catch — you can't have all three at once.
CHIA

The part that runs the search

CHIA is the orchestration layer. It decides which combination to try next, checks it makes sense, runs it, scores it, and feeds the score back in — so the search gets smarter with every round.

These five parts pass work around in a circle. Follow the arrows!
Two sides, one design

The program and the chip, designed together

Normally someone writes the software, then someone else picks the hardware and hopes for the best. We change both at the same time and see which combinations actually work well together.

Simulating a whole AI model chip-by-chip would take forever — so we test the busiest part instead.

How we test

One trip around the loop

Pick a setting. Check it makes sense. Run it on both sides. Collect the numbers. Compare it against everything tried before — then pick the next setting.

Every experiment starts with a checklist: model, hardware, parameters, constraints.
What we measure

Three scorecards

For every setting we turn, we write down three kinds of result.

Speed, memory and correctness — a fast run that gets the answer wrong doesn't count!

Speed

Cycles — total work done
Instructions — steps taken
Efficiency — work per step
Time — how long it would really take

Memory behaviour

Near misses — times the scratchpad was empty
Far misses — times it had to reach further out
Fewer misses means a faster, cooler chip.

Correctness

Checksum — the answer is verified
Pass / fail — a fast run that gets it wrong doesn't count
The result

The setup worth building

Out of everything the search tried, one combination of program settings and chip settings comes out ahead: fast enough, small enough, cheap enough — and correct.

And that's the one we'd actually build. Every claim on this page is backed by a measured run.

Small enough

Still correct
